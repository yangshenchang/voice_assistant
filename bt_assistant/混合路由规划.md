> 旧 realtime 方案见 `Hermes语音助手混合架构实施方案.md`：**路由思想保留，模型与后端已替换**

## 一、方向变更（继承什么 / 替换什么）

| 维度 | 旧实现 | 新方向 | 影响 |
|---|---|---|---|
| 语音链路 | `qwen3.5-omni-flash-realtime` 单 WS 端到端 | **本地三段式**: VAD → STT → LLM → TTS | 多出 STT 与 TTS 两处"首包"，靠低时延策略压 |
| 唤醒 / 判句 / 打断 | 服务端 `server_vad` + `response.cancel` | 本地 KWS + 振幅 VAD + txn 打断 + 回声抑制（工程已实现，不改） | 可控；回声抑制要自己做 |
| 会话形态 | 单一长 WS（300s idle 断连 → 需保活） | 每轮短请求 + 本地历史 | **保活需求消失**；改为本地上下文管理 |
| 工具 / agent 后端 | Hermes（`hermes chat` 子进程） | **dsh**（常驻 qqbot profile 内的 agent） | 见第三、四节 |
| 路由决策者 | realtime 模型自己（工具描述引导） | **前端 LLM 自己**（deepseek-flash tool calling） | 保留 |
| 后台任务 +【系统】旁白 + 延迟播报 | 有 | **保留**（机制照搬，触发器改造） | 见第五节 |

**一句话**：快链路 = 工程三段式 pipeline；慢链路 = 常驻 dsh agent；两者之间的路由、后台播报与 QQ 投递 = 旧 `realtime_bridge.py` 的混合路由思想 + 本轮的实测修正。

## 二、目标形态（已收敛）

```
[常驻] dsh --profile qqbot 进程（QQ 机器人本来就要常驻 → 冷启动摊薄为零）
   ├─ 每个 QQ peer 一个 agent session（sessionId 确定性派生，可 resume = 长期记忆）
   ├─ 中继插件（新增）: 挂本地控制通道
   │    ① 入站  : 语音侧提交 {task} → getOrCreate(peer, msgId 留空) → agent.followup(task)
   │    ② 进度  : 订阅 session 事件(工具生命周期/消息/思考) → 转发语音侧
   │    ③ 完成  : 最终消息 → 语音侧(供摘要) ；全文 → qqbotPush(openid, 分块 ≤4500)
   └─ 改造前置: peer→openid 持久化 + ctx.provide('qqbotPush') + 凭据外置

[本地] 语音助手进程（三段式）
   快链路 : KWS → VAD → STT → 前端LLM(工具: 时间/天气/IoT + delegate) → TTS
   复杂路径: 收到 tool name(~0.8s) → 播确认话术 → 委托 → 进度累计
             → 结果摘要 → 空闲/轮次结束时播 → 全文推 QQ
```

## 四、实测结论（V1–V4，2026-09-13）

| 项 | 实测 | 设计含义 |
|---|---|---|
| 前端 LLM 关思考 + tools | **可用**（HTTP 200，`finish_reason=tool_calls`） | 无需在"首字快"与"能用工具"之间二选一 |
| 工具调用轮的文本 | **content 恒为 0 字**（两个用例） | "用户说完→长时间静默"是默认行为 → 兜底确认话术是**必需项** |
| prompt 要求"调工具前先说一句" | **有效**：产出「好的，我去查一下。」，526~1043ms 到达 | 确认话术**优先用模型自产句**，仅当本轮文本为空时用本地模板补（避开重复播放） |
| 确认话术最早开口时刻 | 工具名到达 ≈ **774~816ms**（不必等 arguments 拼完，参数可达 40~170 字 / 21~119 分片） | 收到 `function.name` 即开播，同时继续收参数 |
| tool_calls 分片形态 | `delta.tool_calls[i].index` 索引、`name` 仅首片、`arguments` 逐片、结束信号 `finish_reason=tool_calls` | 必须写累加器；现有 `llm/` 只取 `delta.content`，需扩展 |
| 路由准确率（6 用例 × 2 模式） | 时间→`get_current_time`、闲聊→不调、天气→`get_weather`、行情/报告/金价→`delegate` | 全部符合预期；开/关思考路由一致 |
| 快路径 TTFT | 复用连接 **中位 702ms**；新建 client 额外 **2954ms**（SSL 上下文） | 连接复用是硬要求（实测坐实 demo 注释） |
| ACP 冷启动 | **27.3s / 复测 33.2s**（非一次性开销） | 每任务一进程不可行 → **常驻**是必需 |
| ACP 进度事件 | 工具级生命周期 + 思考增量 + `usage_update` + 已提交消息，全带时间戳 | 进度数据源达标；另含 `session/resume`（长期记忆）、`session/request_permission`（客户端可当审批应答者） |
| headless 单任务 | 简单查询 46.7s；报告任务 136.9s | 进一步印证常驻必要 |
| headless 文件约定 | **被违反**：未生成 `report.md`，全文 2766 字 markdown+表格打在 stdout | 双产物不能只靠任务描述约束（见决策 2） |
| 输出可朗读性 | 报告类 = markdown+表格（不可直接播）；查询类 = 74 字干净口语（可直接播） | 语音侧必须**无条件**清洗 + 摘要 |
| QQ 主动推送（平台侧） | **可行**：个人认证即可，20/qpm、1000 条/用户/日，Markdown 全量开放；前置=好友关系 + 用户未关"允许主动发送"；被动窗口仅 60min/4 次 | 方案 b 成立 |
| QQ 插件（本机） | WebSocket 网关；发送唯一出口 `bot.sendMarkdown(replyTarget, chunk)`；**无任何主动推送入口**（仅 `inject=['agents']`）；**openid 未持久化**；无 `ctx.provide` | 需两步小改造（见第六节） |

## 五、路由与后台机制（继承 + 新约束）

1. **决策者是前端模型自己**：靠 `delegate_to_dsh` 工具描述引导（旧描述可直接改写），实测路由准确。
2. **任务描述必须自包含**：agent 看不到语音对话历史。
3. **确认话术**：模型自产优先 → 文本为空时本地模板兜底；**只播一次**（约定由谁负责，另一侧闭嘴）。
4. **进度播报**：累计后一次性播（"正在查询→正在分析"逐条播是噪音）；触发器从旧的"WS 空闲计时"改为**"用户已等待时长"**；**进度不进会话历史**（本地历史仅 20 条预算，且每条都在后续每一轮重复付 token 与首字）。
5. **结果播报时机**：announcement 队列 + 状态机；"可播"判定必须含 `not vad.is_recording(sid)`（否则回声抑制会静音 VAD、把用户正在说的话截断）+ 300ms 宽限；优先级 用户轮次 > 结果 > 进度；用户开口必须能打断播报。
6. **结果回灌**：只进压缩结论；**不走 `role:"tool"` 消息回灌**（`assistant.tool_calls` 与其结果必须成对，历史裁剪一旦拆散即 400）。
7. **轻量操作**：时间/IoT 建议本地直连（模板应答），不经 LLM 二次往返；天气走 LLM+tool。

## 六、风险与硬约束

1. **审批缺失（P0）**：默认沙箱放行 `pwsh`/`glob`（实测全程无审批请求）→ 语音误路由 = 语音直通 shell。中继阶段必须**显式限定工具集/沙箱**，副作用类操作加语音确认。
2. **数字真实性（P0）**：V4 报告给出完整价格表与点位（"9/11 收 3888.11"），本地无法验证。语音播错数字用户几乎无法察觉 → 全文报告必须带来源；语音摘要避免裸数字或注明来源。
3. **静默兜底（P1）**：工具轮 content 为 0 是常态，必须有兜底确认话术，否则用户以为助手死了。
4. **QQ 前置改造（P1）**：① peer→openid **持久化**（当前仅内存，重启即丢）；② `ctx.provide('qqbotPush')` 暴露 `pushC2C(openid, markdown)`（`bot.sendMarkdown({scope:'c2c', targetId:openid})`，**不传 msgId** → SDK 自动走主动通道）。另两个坑：出站需 `manager.findBySessionId` 命中 record，否则**静默不发**；旧 `replyTarget.msgId` 会让推送被当被动回复而过期报错。
5. **凭据**：`~/.dsh/profiles/qqbot/cordis.patch.yml` 中 appSecret **明文**，应改环境变量注入。
6. **回声抑制吃话**：见第五节第 5 条。
7. **可取消性**：用户"别查了"需终止 delegate（常驻模式下是取消 agent turn，不是杀进程）。

## 八、Phase E — 真机联调发现的问题（已修）

用户实跑 `run.py` 时反馈"自动退出了两次"。日志定位到**两个真实 bug**（都不是崩溃，而是"静默失效"）：

### E1 结束词误判 → 助手"自己睡过去了"
- **现象**：`天气查好了吗？` / `刚才那个天气查好了吗？` 各触发一次 `End word in session` → `awake ended by end word` → 回到待唤醒态，之后不喊唤醒词就不再应答（用户感知为"自己退出"）。
- **根因**：`_has_end_word()` 是朴素子串匹配 `any(ew in text for ew in end_words)`，而 `END_WORDS`（81 条）里有 **"好了"**、以及 `行了/收到/了解/懂了/可以了/知道了` 等日常词。
- **最终修法（两头一起收干净，而不是靠更聪明的匹配去猜）**：

  **① 词表侧：81 → 60 条，剔除 21 个歧义词**（歧义来自词表，不来自匹配方式）：

  | 剔除 | 原因 |
  |---|---|
  | 好了 | 「查好了吗」「做好了」—— 本次事故元凶 |
  | 行了 / 行了好吧 | 「就行了吗」等日常用法（保留 行了行了 / 行了吧） |
  | 好嘞 | 日常应答（"好嘞，谢谢"），不是结束 |
  | 了解 | 「了解一下…」是常见请求 |
  | 收到 | 「收到消息」；口语应答也常说 |
  | 懂了 / 知道了 / 已阅 | 陈述性应答，未必表示结束 |
  | 可以了 | 「这样可以了吗」 |
  | 够了 | 「钱够了」「够了没」 |
  | 下去 | **语义反转**：「说下去」= 让你继续 |
  | 你继续 | **语义反转**：「你继续说」= 让你继续 |
  | 就这样 | 「就这样做吧」= 按这个方式继续（保留 就这样吧） |
  | 歇着 | 保留 歇着吧 |
  | 停 / 拜 | 单字，误伤「停车」「拜年」 |
  | 结束 | 「会议结束了」等陈述 |
  | 退下吧 / 你退下 / 跪安吧 | 已被 退下 / 跪安 的子串覆盖，冗余 |

  run.py 里保留了这份"已剔除清单+原因"的注释，防止以后有人再加回来。

  **② 逻辑侧：只留一条守卫 —— 疑问句不算**（以 吗/呢/么/嘛/？/? 结尾）。
  原先那套"按词长分层（整句/句首/句尾/单字只认整句）"的匹配规则**已删除**：词表收干净后它不再必要，且规则越复杂越难维护。

- **已知取舍**：单独说「好了」现在**不会**结束会话（因为它无法与「做好了」这类陈述区分）。想恢复的话，把它加回 `END_WORDS` 即可 —— 有了疑问句守卫，你实机踩到的那两句（`…查好了吗？`）不会再误判，但「天气查好了」这种陈述句仍会误判。
- 回归：`verify/e1_endword_announce.py` 34 条用例（含实机两句 + 全部删除词 + 语义反转词）全过。

### E2 排队播报永久丢失（重入 bug）
- **现象**：委托结果在"正在放音"时被推迟（`[announce] 会话忙, 排队等空闲`），此后日志里再无任何播报记录 —— 结果永远没播出来。
- **根因**：`_schedule_announce_retry()` 的重试任务自己调 `flush_announcements()` → 仍忙 → 再调 `_schedule_announce_retry()`，而此刻 `self._announce_retry` **正是这个正在运行的任务**，`not done()` 成立 → 直接 return → **重试链断裂**。
- **修法**：换成**常驻单 worker**（`_announce_worker`，每 0.5s 看一次队列，空闲即播），彻底消除自引用路径；`warmup()` 启动、`shutdown()` 收尾。同时队列去重（同一条不重复入队）。
- 回归：`e1_endword_announce.py` 的 Bug 2 用例（忙→空闲后确实播出）+ 完整委托链路重跑。
