# 语音助手 · 低时延规划

> 版本: v0.1 ｜ 日期: 2026-09-13 ｜ 状态: 规划中
> 来源: `fastest_demo.py` 实测策略提炼 ｜ 定位: 只承载低时延相关内容，后续按主题追加章节
> 架构与路由主线见 `混合路由规划.md`；旧 realtime 方案见 `Hermes语音助手混合架构实施方案.md`

---

## 一、总纲

**全链路时延 = 各段串联开销 + LLM 首字 + TTS 首包。** 优化只做两件事 —— **砍掉一次性开销**、**让每段的首个产物一到就往下游流**（不攒、不等整句）。

三个测量口径（缺一不可）：

| 口径 | 含义 | 用途 |
|---|---|---|
| 说话结束 → 首字 | 服务语义 TTFT（STT 完成 → LLM 首 token） | 衡量模型/网络 |
| 说话结束 → 出声 | **用户感知总时延**（→ 首个音频包） | 验收基线 |
| 说话结束 → 说完 | 整句/整段音频送完 | 衡量冗长度 |

## 二、已验证的低时延策略（源自 `fastest_demo.py`）

| # | 策略 | 具体做法 | 依据 / 效果 |
|---|---|---|---|
| 1 | 连接复用 | LLM 的 `httpx.AsyncClient` 只建一次，全程复用 | **已实测坐实**：新建 client 构造 SSL 上下文 **2954ms**；复用后首字中位 **702ms** |
| 2 | 启动预热 | 启动时先建 SSL / TTS 首条 websocket，与其它初始化并行 | 否则这些一次性开销全落在第一轮的首字延时里 |
| 3 | 关思考模式 | 请求显式带 `thinking={"type": "disabled"}` | 跳过思维链，首字立即返回（语音场景不需要推理展示） |
| 4 | 约束输出 | `max_tokens=300` + system prompt「最简短中文口语，禁 Markdown/emoji」 | 首字更快、说完更快、TTS 音频更短；同时避免 TTS 念符号/emoji 名 |
| 5 | 按句切分 | 句末标点（`。！？.!?`）切句，逐句送合成 | 不等整段 LLM 输出完，首句先出声 |
| 6 | TTS 流式 | `streaming_call` + `streaming_complete`，回调 `on_data` 一到就写扬声器 | 首包 ~0.6–0.8s，到达即出声，不等整句合成完。**踩坑**：SDK 的 `call()` 在本机 dashscope 1.25.14 上只停在 task-started，拿不到音频 |
| 7 | 音频格式直通 | 统一 PCM 16k / 单声道 / 16bit，直接写 pyaudio | 无解码、无重采样、无 ffmpeg（对比 edge-tts 路径要整句 mp3 + ffmpeg 转码） |
| 8 | 采集与 VAD 轻量 | 512 帧（32ms）分块；纯振幅阈值 VAD + 0.5s 静音判句；preroll 5 帧 | 判句粒度细、开销近零；preroll 防吃掉句首 |
| 9 | 阻塞移出事件循环 | ASR / TTS 合成放 `asyncio.to_thread`；每块音频后 `await sleep(0.0001)` 让出 | 采集与播放不被网络调用卡住 |
| 10 | 无状态单轮 | demo 去掉了唤醒/打断/历史，每轮独立 | 历史不长 → 首字不随对话变慢；也是最小可测基线 |

## 三、对本方案（三段式 + dsh 混合路由）的含义

- 前端链路正是这 10 条策略的作用对象：与 realtime 方案相比多了 **STT 与 TTS 两处"首包"**，这 10 条就是把它们压掉的手段（连接复用 / 预热 / 流式即播 / 格式直通）。
- **delegate（dsh）必须走异步旁路**：绝不串进前端链路 —— 提交后立即返回，结果回来再播；否则一次 delegate 会把"首字"从几百毫秒拉到几十秒。
- 混合路由不改变前端链路，只决定"谁来答、答多长"；答得短 = 说完得快 = 用户感知时延更低。
- 可直接照搬：预热（前端 LLM 连接 + TTS 首连）、PCM 直通播放、prompt 约束短口语、流式 delta 一到即播（不攒缓冲）、三个测量口径。
- dsh 冷启动已实测（见第四节）：**必须常驻**，"每任务一进程"会把首字拉长 30s 级。

## 四、实测基线（2026-09-13，本机）

| 环节 | 实测 | 备注 |
|---|---|---|
| `httpx.Client()` 构造（SSL 上下文） | **2954 ms** | 一次性，但**每次新建都要付**；预热/复用的价值就在这里 |
| 前端 LLM 首字（**复用连接**，闲聊） | **中位 702 ms**（613/735/836/669 ×4） | 快路径真实 TTFT 基线 |
| 首请求（新建连接） | 头 204 / 首字 773 / 收尾 919 ms | 冷连接只多 ~70ms，大头在上下文构造 |
| 工具调用轮 | 首字节 157~239 / **工具名 774~816** / 收尾 845~855 ms | content **恒为 0 字** → 需兜底确认话术 |
| 加"调工具前先说一句" | 首文本 **526~1043 ms**，产出「好的，我去查一下。」 | 确认话术优先用模型自产句 |
| dsh 进程冷启动（ACP 实测） | **27.3s / 复测 33.2s** | 每任务一进程不可行 → 常驻（参考 `混合路由规划.md`） |

**测量纪律**：任何 LLM 时延测量都必须复用 client，否则每个样本都被 SSL 构造污染（本阶段第一次测量就是这样被污染的，v3c 与 v3d 即为污染/修正对照）。

### 4.1 组件基线（真实服务，2026-09-15，`verify/d1_component_baseline.py`）

| 组件 | 实测 | 说明 |
|---|---|---|
| STT（qwen3-asr-flash，整段） | **~0.5–0.9s**（中位 717ms） | 3.55s 与 5.61s 音频耗时接近 → **基本不随音频时长增长**；首次含冷连接开销 |
| LLM 首字（闲聊，复用连接） | **0.54–1.05s** | ⚠️ 这里测到的是**首个可合成句子**到达时间（`chat_stream` 要等到句末标点才切句），并非首个 token |
| LLM 工具轮 | 首文本（确认话术）**0.59–0.73s**；工具调用 **0.62–0.75s** | 与 V3d 一致 |
| TTS 首包（CosyVoice v3-flash） | **0.59–0.96s**（中位 673ms） | 与文档记载的 0.6–0.8s 一致；整句合成耗时随字数（9 字 1.1s / 40 字 2.5s） |

**串联预测（说话结束 → 出声）**：快路径 ≈ **2.2s**；时间工具（含二次 LLM 往返）≈ **2.6s**；复杂路径确认话术 ≈ **2.0s**。
以上不含 VAD 判句的 0.5s 静音等待与声卡缓冲，麦克风实测会略高。

### 4.3 因子实验：LLM 那 1.5~1.7s 到底来自哪（`verify/d2`–`d7`）

**五个假设，前四个被否掉，第五个命中**：

| # | 假设 | 实验 | 结果 |
|---|---|---|---|
| 1 | system prompt 太长 | 短 prompt(39字) vs run.py prompt(284字) | **短 prompt 反而更慢**（834 vs 608ms）→ 否 |
| 2 | 工具 schema 拖慢 | 0 工具 vs 2 工具 | 608 → 905ms（≤300ms 且噪声大）→ 非主因 |
| 3 | 对话历史累积 | 0 / 8 / 20 条 | 905 → 815 → **747ms** → 否 |
| 4 | 等句末标点才能合成 | 首 token vs 首分句 vs 首句末；两批问题（短答 + 长首句） | 可省中位 **65ms / 93ms** → 否（`option_split_threshold` 不值得调） |
| 5 | 连接被回收需重握手 | 连续 / 静置 45s / 静置 90s | 响应头 158 / 146 / 188ms → 否 |
| **6** | **麦克风阻塞读卡住事件循环** | **真实 AudioDeviceAdapter 开麦 A/B**（`d7`） | **命中** |

**命中项的实测证据**（`verify/d7_real_adapter_impact.py`，真麦克风 + 真 VAD + 真 KWS + 真 LLM）：

| 指标 | 不开麦 | 开真麦（修复前） | 差值 | 修复后（开真麦） | 差值 |
|---|---|---|---|---|---|
| 请求→token | 445 | 700 | **+255** | 507 | −14 |
| token→句 | 146 | 500 | **+354** | 162 | +5 |
| LLM 段合计 | 591 | 1200 | **+609** | 669 | ≈0 |

**根因**：`adapter.start_listening()` 里 `stream.read(512)` 是**同步阻塞调用，直接跑在事件循环线程上**，每 32ms 卡一次循环 → SSE 增量被"晚处理"，于是 `请求→token` 与 `token→句` 一起被拉长。整个链路凭空多出 **~600ms/轮**。

**修复**：麦克风读取移入独立线程（`mic-reader`），经 `asyncio.Queue` 交给事件循环（满则丢最老一块，上限约 3.2s 音频）；VAD/KWS 逻辑一行未改。修复后开麦与不开麦的差值归零。

> 为什么前一轮的 `d5` 没测出来：它用 `await asyncio.sleep(0.032)` 喂音频 —— 那是**让出**事件循环，而真实 adapter 是**阻塞**它。模拟负载时这个区别是决定性的。

**另外修掉的一处**：`adapter.stop_response()` 原先每轮无条件 `_close_play_stream()`（哪怕什么都没在放），已改为无流/未播放/队列空时直接返回（实测 `请求前` 中位 94ms，个别轮次因确实在放音而达 237~520ms，该修复只在这类轮次起作用）。

### 4.4 麦克风实测采集器（`perf.py` + `run.py`）

`run.py` 已接入 `PerfRecorder`：每轮按**路径**（`chat` / `tool` / `delegate`）把时延落盘到
`bt_assistant/perf_baseline.jsonl`，Ctrl+C 退出时打印分路径汇总。列含义：

```
路径 | 样本 | 总时延中位/最短/最长 | STT | 请求前 | 请求→token | token→句 | LLM首句 | TTS首包
```

- `请求前` = 停上一轮播放 / 组 prompt / 事件循环调度等**本地**开销（不含网络）
- `请求→token` = HTTP 往返 + 模型吐首个 token
- `token→句` = 从首个 token 到出现句末标点（能切出第一句送合成）的时间

复杂路径的"总时延"口径是**确认话术出声**，最终答案属异步播报、不计入 —— 否则统计会被几十秒的委托时间污染。

**麦克风实测注意**：
- 本机输出设备实测为 `扬声器 (小爱音箱-9138) @ 44100Hz`（无线音箱），播放链路自身可能额外带来百毫秒级缓冲 —— 实测时延若明显高于 4.1 的预测，先怀疑设备侧。
- 采集器已随 `run.py` 启动打印落盘路径；退出时按路径打印汇总（样本太少时中位数不可信，工具/委托路径建议各跑 3 次以上）。
