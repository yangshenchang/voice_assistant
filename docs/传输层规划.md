## 一、为什么要有传输层

改造前 `adapter.AudioDeviceAdapter` 与 pipeline 是**硬连**的：它在构造函数里直接改写
`sts.handle_response` / `sts.stop_response`（`adapter/__init__.py`）。于是"音频必须来自
本机声卡"被焊死进编排逻辑 —— 想接第二个音频端（手机）就无处下手。

```
pipeline ──┬─ LocalTransport    本机麦克风 + 扬声器（行为与改造前逐字一致）
           └─ RemoteTransport   手机等远端（WSS 上行音频 / 下行 TTS / 主动播报）
```

一句话：**pipeline 只认接口，不认设备。**

## 二、这一层负责的三个语义（容易写错的地方）

| 语义 | 规则 | 不这么做会怎样 |
|---|---|---|
| **按会话路由** | 显式绑定 > 前缀匹配 > 本机兜底 | 本机在放音时手机发起一轮，音频会串到扬声器 |
| **仲裁"谁在说话"** | 主动播报要求**没有任何端在录音** | 手机用户说话中途被播报插嘴（本机侧有回声抑制，远端没有） |
| **落历史的归属** | 本机无条件写；远端按"是否真被中断"写 | 把从未播出的内容记成"说过"（助手自己不知道讲过什么） |

**远端"在录音"只能由远端报告**，服务端无法像本机那样从 VAD 得知。实现方式是记录
"最后一次收到上行音频的时刻"，在 `RECORDING_WINDOW`（默认 0.5s，与 VAD 静音判句阈值
同量级）内算作在录。从**音频到达服务端**起算，而不是等 VAD 判句 —— 判句会晚约
0.5s，那时用户早说完了，用它当信号等于没保护。

### 3.1 兼容性设计（两条退路都留着）

* `transport_registry=None`（默认）→ `handle_response` / `stop_response` 仍是外部回调，
  完全等价于改造前；`_is_idle()` 的第四条恒不成立。
* `attach_transport()` 只接管 `handle_response`（为了多端路由），**`stop_response` 留在
  adapter 上** —— 停止播放是本机设备的职责，而"是否真的中断了"由 `LocalTransport` 在
  流水线里单独问 adapter 得出，不必让 pipeline 去碰 adapter 内部状态。

### 3.2 踩坑记录（写代码时真实发生的，已用测试锁住）

**把 `stop_response` 的返回值当成"有没有播放过" → 本机助手失忆。**

`AudioDeviceAdapter.stop_response()` 是旧式回调，**返回 `None`**。而 `None` 在布尔判断里
是假 —— 若按"返回值真才写历史"实现，本机路径就**再也不写历史**（模型刚说完就忘了自己
说过什么）。

正确判据是**会话归属哪个端**，不是返回值真假：

```python
本机会话 → 无条件写（与改造前一致）
远端会话 → 按该端汇报的 "是否真被中断" 决定
```

回归：`f0_transport_layer.py` 的 E1~E10（`E1 本机 + None 仍要写` 就是这条的守门用例）。

## 三之二、文本端（阶段 0.5，已完成并真机验证）

### 为什么做

改造前想验一轮对话**必须对着麦克风说话**：没有 key / 没有声卡（如持续集成、远程排查）
完全无法验证，每改一处逻辑都要"说一遍再听一遍"。文本端把"音频从哪来"换成 stdin，
**复用同一条 `pipeline.invoke` 与同一套 transport 装配**。

```bash
python run.py --text              # 交互；每轮后等 60s 后台委托
python run.py --ask "现在几点了"    # 问一句就退
python run.py --ask "查今天上证指数" --wait 300   # 等后台委托跑完并播出结果
python run.py --text --with-tts    # 仍走真实 TTS（需 DASHSCOPE_API_KEY）
```

文本模式默认**不合成**，因此**只需要 `DEEPSEEK_API_KEY`**。

### 真机验收结果（2026-09-22，真 deepseek-flash + 真中继）

| 路径 | 实测 | 结果 |
|---|---|---|
| 纯知识 | `你好` → `你好，我是小牛，有什么可以帮你的吗？` | 首句 **1042ms**（请求→token 842） |
| 多轮上下文 | 追问"我刚才问你什么了" → 正确复述 | **历史写入正常**（失忆 bug 未复发） |
| 本地工具 | 显式要求 → `get_current_time` 真被调用，自产确认话术 | 首句 **656ms** |
| 复杂委托 | 确认话术 → 等待 → 结果播报 + QQ 推送 | 首句 **780ms**；结果如期回播 |

**一条真实数据**：`查询今天A股北证50指数的收盘点位` → 结果播报
「九月二十二日北证50指数收在一千零四十六点八零点，跌了百分之一点零八」，
并附「详细的我发到你 QQ 上了」—— 说明阶段 0 的**整条架构**（transport 路由 +
委托 + 异步 emit 播报 + 历史回灌）在真模型下是通的。

### 这一阶段挖出的 5 个真 bug（都已修 + 加回归锁）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 文本模式委托播报**必崩** | `pipeline.announce` 挡住后仍调自己的 `_speak` → `NullSpeechSynthesizer` 抛错 | 新增 `AudioTransport.emit()`：**何时说**留在 pipeline 队列，**怎么说**交给端 |
| 2 | 文本模式主线走不通 | pipeline 主链路**无条件**调 `tts.synthesize_stream` | 加 `text_only` 分支：文本直接交给端，不合成 |
| 3 | `ask()` 永远返回空串 | `invoke` 是**生成器**，投递（`handle_response`）只在内部消费者 `_on_speech` 里做；自己驱动 invoke 就必须自己投递 | `ask()` 里逐条 `await self.handle_response(resp)` |
| 4 | 确认话术**播报两遍** | `handle_response` 把 `print` 放在 `if response.text:` 之外 → 播报结束的"无文本 final"用残留 `_reply` 又打一遍 | 打印收进 `if response.text:` 内 |
| 5 | 结果播报可能重复 | `_announce_result` 缺幂等保护 | 加独立标志位 `result_announced` |

另外顺手修了两处**语义/元数据**问题：

* chunk 的 `text`/`voice_text` 原来取"最后到达的 chunk"，一段话分多句时会重复；
  现在取**本句**（播放层只读 `audio_data`，语音链路行为不变，但远端/文本端要拿文本就正确了）。
* `_drain_queue`（兜底播出排队播报）与常驻 worker 存在重复播报竞态，判据统一为
  "**仍在队列里**才算没播过"。

### 设计原则（值得记住）

> **队列与时机是跨端统一的（留在 pipeline），发声方式是端相关的（交给 transport）。**

这条也是"文本端能跑通"的前提：它证明 pipeline 确实只依赖接口，不依赖声卡。


## 四、移动端目标形态

```
手机 App（音频终端，不是"第二个助手"）
  ├─ 本地 KWS（sherpa-onnx，唤醒前零上传）        ← 省电 / 不被系统杀 / 不耗流量
  ├─ 麦克风采集 16k/16bit/mono，512 帧(32ms) 分块 ← 与本机同格式，零重采样
  ├─ 播放服务端 PCM（TTS 原样直通）
  └─ 一条 WSS 长连（复用：上行音频 + 下行 TTS + 服务端主动播报）
              │
        [公网入口]
              │
PC 或 NAS 上的语音服务（现有链路 + WSSTransport）
  └─ 委托结果：手机在线 → 推给手机；离线 → 走 qqbot_relay 推 QQ（已可用）
```

### 4.1 唤醒词为什么必须在手机上

Android 后台持续开麦受系统省电策略与后台音频限制的约束，且"一直推流给服务端判唤醒"
意味着**唤醒前就持续上传音频** —— 耗电、耗流量、还可能被系统杀。正确形态是：

* 手机本地跑 KWS（沿用现有 3.3M 模型与词表「小牛」，sherpa-onnx 有官方 Android 绑定）；
* 命中后才建连推流；一轮结束或静默超时即断开。

代价（要诚实说）：**网页/PWA 做不到这件事**（页面不可见时麦克风与后台音频受限）。
所以 PWA 只能当"打开页面→按住说"的对讲机，用来验证通道与时延；
**"随叫随到"必须有原生 App**。

### 4.2 戴着耳机顺带解决的两个老问题

1. **回声抑制不再必要** → 播报期间麦克风不必静音 → **用户说话可以打断播报**
   （本机路径目前做不到，见 `docs/混合路由规划.md` 待确认第 6 条）。
2. 手机端不需要实现回声抑制，代码更简单。

| 方案 | 做法 | 前提 |

⚠️ **安全底线**：不要把 `127.0.0.1:3080`（DSH Web GUI，内置 `pwsh` 全权限 agent）

## 七、协议要点（阶段 2 定稿）

| 项 | 约定 | 理由 |
|---|---|---|
| 传输 | 单条 WSS 长连，二进制帧 | 一条通道复用三件事：上行音频 / 下行 TTS / 主动播报 |
| 音频 | 16k / 16bit / mono **原始 PCM，不压缩** | 与现有链路一致，零重采样零解码；约 256 kbps，可接受 |
| 分块 | 512 帧 = 32ms | 与本机 `input_chunk_size` 一致，VAD 判句粒度不变，可沿用既有基线 |
| 会话 | 远端会话带前缀 `phone:`；一次性 token 配对 | 避免与本机 `default_user` 混淆；安全底线 |
| 事件 | `wake / start / final / announce / error` | 现有 `STSResponse.type` 已是这个形状，直接映射 |
| 采样率 | 下行 chunk 必须带 `metadata["sample_rate"]` | 手机侧要拿它开播放器 |

**以上约定已在阶段 1 落地为代码**：`protocol/__init__.py`（纯编解码，可离线单测）+
`transport/websocket.py`（服务端 I/O）+ `web/*.js`（网页端 I/O）。协议版本号
`PROTOCOL_VERSION=1`，握手期校验，错配**明确报错**而不是行为诡异。

### 7.1 二进制帧格式（4 字节头）

```
byte 0     : 0x01=上行音频  0x02=下行音频
byte 1     : 保留
bytes 2-3  : 小端 uint16 序号（回绕）
```

### 7.2 控制帧（JSON）

| 方向 | 类型 | 说明 |
|---|---|---|
| C→S | `hello` | `{version, token, sampleRate, frameSamples}`，**必须首帧** |
| C→S | `start` / `end` | 按住/松开（服务端据此维护"用户在说话"） |
| C→S | `cancel` | 打断当前轮 |
| C→S | `ping` | `{t}` 延迟探测 |
| S→C | `ready` | `{protocol, sessionId, sampleRate, frameSamples}` |
| S→C | `state` | `{idle, speaking, recording}` —— **客户端据此决定能否推流** |
| S→C | `text` / `stt` / `announce` | 助手文本 / 识别结果 / 主动播报 |
| S→C | `pong` / `error` / `bye` | 延迟回显 / `{code, message}` / 断开原因 |

错误码：`bad_version` / `unauthorized` / `bad_message` / `duplicate_session` / `internal`
（客户端应按 **code** 分支，不要匹配 message 文本）。

## 七之二、阶段 1 实施记录（服务端 + 网页端）

### 起服务

```bash
python run.py --serve-remote                  # 局域网监听 0.0.0.0:8801，自动生成口令，**默认 TLS**
python run.py --serve-remote --no-local-mic   # 只服务远端（本机没有声卡时）
python run.py --serve-remote --no-tls         # 关掉 TLS（手机端麦克风会被浏览器拒绝，仅调试）
python run.py --serve-remote --token mypass --wait-connection 60   # 固定口令并等手机连上
```

启动后会打印手机可用的地址（自动探测本机局域网 IP）、证书指纹与口令。

### TLS 是**可用性前提**，不是"可选项"

浏览器只在**安全上下文**里把麦克风给页面，而 ``http://192.168.0.8:8801`` 属于
不安全来源（``http://localhost`` 是例外）→ Chrome **直接拒绝 getUserMedia**，
现象是"按住说话没反应"，极易被误判成代码坏了（实测踩到）。所以 ``--serve-remote``
**默认开 TLS**，用自签证书：

* 证书由 `transport/tls.py` 首次运行时自动生成到 `data/certs/`，之后**复用**
  （否则手机每次都要重新信任一次，很烦）
* RSA 2048 / SHA256 / 825 天，**必须带 IP SAN** —— 只写 CN 的话现代浏览器会因
  "证书缺少使用者备用名称"**直接拒绝连接**（不是只警告）
* 手机首次访问会提示不安全 → 「高级 → 继续访问」即可；要核对身份就用启动时打印的
  **证书指纹**
* 顺带解决了局域网音频**明文**的问题（16k PCM 原来是裸奔的）

需要 ``cryptography``（已加入 `requirements.txt`）。私钥权限只在 POSIX 上收敛为
0600 —— Windows 的 `chmod` 只映射只读位，对目录设 0o600 会把它变成**拒绝访问**
（实测把临时目录都弄坏了）。

### 三条关键实现决策

1. **上行泵（队列 + 丢最老）**：网络读协程只做"入队"。若在读协程里直接 await
   `feed_audio`，一旦下游被拖住，网络读也跟着停 → 上行积压、时延飙升。
   这是本机 adapter"阻塞读卡住事件循环"那个坑的网络版（`docs/低时延规划.md` 4.3）。
2. **下行独立队列 + 满则丢最老**：宁可让用户听到"跳过一小段"，也不让整条链路
   积压到秒级延迟。回归用例见 `f2` 的 F5~F7。
3. **播报走独立队列且有优先级**：本轮 TTS 优先于主动播报 —— 播报是异步结果
   （等多久都还能再说），而用户正等着听回复。

### 挖出的 16 个真 bug（都已修 + 加回归锁）

| # | 现象 | 根因 |
|---|---|---|
| 1 | 客户端连不上（`InvalidStatus: HTTP 404`） | `process_request` 把 **WebSocket 升级请求**也当静态请求处理了 → 必须按 `Upgrade` 头放行 |
| 2 | 客户端一直收不到音频 | 发送队列里"音频"塞的是**裸 PCM**，而公告/文本塞的是 `(kind, payload)` 元组 → 发送协程 `too many values to unpack`。**同一队列必须只有一种元素约定** |
| 3 | 手机说话没反应（音频只堆在队列里） | 上行泵只在收到 `start` 控制帧时才启动；客户端若先推流后补 `start`，音频永远不会被处理 → 改为**懒启动** |
| 4 | **主动播报永远不开口** | 会话断开后 `session_prefix` 仍然命中 → 注册表一直认为"远端有人在说话"。修法：新增 `AudioTransport.is_active()` 与 `TransportRegistry.owner()`，**仲裁用精确归属，路由才用前缀兜底** |
| 5 | 手机上报 `expected hello` 后断开 | **客户端**在 `ws.onopen` 里先 `await ensureAudio()`（载入 worklet + 弹麦克风权限）才发 `hello` → 服务端 10s 握手超时。**握手不能被 await 拖死**：`hello` 立即发、权限改到按下按钮的用户手势里申请 |
| 6 | Windows 上临时目录/证书目录变成"拒绝访问" | 代码里给私钥 `chmod(0o600)` —— Windows 的 chmod 只映射只读位，对目录设 0o600 会把父目录一起弄坏。改为**只在 POSIX 上收敛权限** |
| 7 | **手机"按住说话"无反应**（2026-09-23 手机实测） | 手机端没有本地唤醒词，服务端 KWS 把音频拦下（`KWS: no wake word, skipping cloud STT`）。修法：新增 `pipeline.request_wake()`，远端连接后"按住说话"即按需唤醒 —— **手势本身就是明确的说话意图**，唤醒词的防误触作用已由它承担。将来手机做本地唤醒词时，命中后调它即可，服务端逻辑不变 |
| 8 | **界面永远显示"服务端还忙着"**（同上，死锁） | `_is_idle` 含 `vad.is_recording()`，而远端会话的 VAD **永远在录音**（手机持续推流、判句被拦）→ idle 恒为假 → 手机被自己拒掉。修法：**远端会话豁免 VAD 那两项**（`vad.is_recording` 是"本机麦克风"的状态，与手机无关；`should_mute` 反映本机扬声器） |
| 9 | **"本机在录音时不开口"这条保护从未生效** | `vad.is_recording(session_id=None)` 写成 `self._sessions.get(None)`，恒为 None → **永远返回 False**。修法：`None` 语义改为"**有没有任何会话在录音**"（VAD 是共享资源，判断"能不能开口"必须问整体） |
| 10 | **一按下就提示"服务端还忙着"、然后再也按不动**（软锁一） | `_is_idle` 把"**用户在说话**"算进了服务端的忙。可对远端来说这个"忙"正是**由客户端自己控制**的（它按着按钮）→ 服务端回 `idle=false` → 客户端据此拒绝下一次输入，**用"自己在说话"把自己锁死**。修法：远端"忙不忙"只看**两件事**——有没有进行中的轮次 + **它自己是否正在放音**（新增 `is_playing()`）；本机侧保持原样（回声抑制会吃话） |
| 11 | **松开后按钮永久停在"稍等…"**（软锁二） | 用户松开那一刻正是 `_active_txn` 非空的瞬间，服务端回 `idle=false`（这是对的），但**之后再没有 state 推送** → 客户端永远等不到恢复。修法：新增 `_schedule_state_push()`，**每轮收尾都重推一次状态**（延迟 0.15s，因为 `invoke` 是在 yield final 之后才清 txn 的） |
| 12 | **一次异常就把整个远端链路永久卡死**（最严重） | `_active_txn` 在 VAD 判句时置位，但**只有"正常收尾"那条路径会清它**。这一轮中途抛错（STT 401、网络断、TTS 失败…）→ txn 永久留存 → `_is_idle` 恒为假 → 手机端再也按不动，**只能重启进程**。修法两道防线：① `invoke` 的 `finally` 里立刻清理（覆盖异常/取消/生成器提前关闭）；② 加 `TXN_STALE_AFTER=30s` 的过期自愈，防连 `finally` 都没走到的极端情况 |
| 13 | **说了话完全没有响应**（真机实测，最关键） | 唤醒豁免只改了**一处**：`_check_awake` 放行了，但 `invoke` **开头的 KWS 前置检查**仍直接读 `self._awake`，而连接时设的是 `_wake_on_connect` → 音频在 STT 之前就被丢掉，日志只留一行 `KWS(streaming): no wake word`。修法：抽出唯一判据 `_skip_wake_check()`，两处共用。**教训：同一个语义出现两处实现，就一定会漏掉一处** |
| 14 | **一轮静默消失**："你好歹得回应点啥" | STT 识别为空（或片段太短）时 pipeline 直接 `return`，**客户端什么都收不到** → 界面永远"稍等…"。修法：新增**轮次结果通知**（`on_turn_outcome`）+ `notice` 事件，任何一轮（正常/没听清/转后台/出错）都必须给一条明确交代；客户端再加**看门狗**（忙超 20s 本地解锁），保证界面永不假死 |
| 15 | 太短/近静音片段白跑云端并必然失败 | DashScope 对过短音频直接返回 `400 The audio is empty`（实测 32ms 必报、1s 正常）。加 `MIN_STT_DURATION=0.35s` 前置判掉，省一次注定失败的往返 |
| 16 | 一句回复刷屏 20 遍 | 下行把同一句文本挂在**每个音频块**上（一句被合成成 20 块 → 20 行）。修法：**音频块不带文本**，文本只由 `final` 给一次；期间反馈用 `stt`/`turn` 事件 |

### 仍未验证 / 已知限制

1. **手机上的真实音质与时延**：需要你实测（本机无音频设备）。
2. **回声抑制**：网页端靠 `getUserMedia({echoCancellation:true})` + "播放期间暂停
   采集"。**戴耳机可完全规避**；免提时若仍有回声，下一步应做服务端 AEC 或缩短
   播放窗口。
3. **自签证书要手动信任一次**：局域网 IP 签不出公信证书，这是内网方案的固有代价。
   公网入口（阶段 5）可换公信证书，届时手机不再需要这一步。
4. **单设备**：目前允许多条连接，但仲裁是保守的（任一远端在说话就不播报）。
   "两台设备同时说话"的策略（建议单会话串行）留到阶段 2 定稿。
5. **缺 DashScope key 时无法真机验收**：`sk-84e1...` 经实测是 **DeepSeek** 的 key
   （DeepSeek 端点 HTTP 200，DashScope 端点 HTTP 401 InvalidApiKey），STT/TTS 需要
   另外的 DashScope key。**没有它时手机端会"说了没反应"**（STT 失败），
   且服务端日志里没有明显提示 —— 这是当前最容易误判为"链路坏了"的情形。

### 调试经验（这次吃了大亏）

**我连续两轮把同一个"失败"结论报错了**，原因是测试脚本连的**不是新代码的服务**：
`job_kill` 杀掉的是 PowerShell 包装进程，**python 子进程活着并继续占用 8801**，
于是新起的服务静默绑定失败，测试一直在连旧实例。

为此固化了纪律：

1. **起服务后必须确认"端口在监听"**（`netstat`）**再**跑测试；
2. 需要区分新旧代码时，看 `/health` 里的指纹/字段，而不是凭"我起了新进程"；
3. 收尾用 `netstat` 找 PID 直接 `Stop-Process`，不依赖 job 包装；
4. 时序类问题必须用时序工具（`f6_press_timing.py`）逐帧打印，
   单看服务端日志（只有 Segment / KWS 行）根本看不出状态机卡在哪一步。
