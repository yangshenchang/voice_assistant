> 版本: v1.0 ｜ 日期: 2026-09-28 ｜ 状态: **局域网已实测可用；公网入口待接入**
> 定位: **实现文档** —— 讲清楚"现在这套东西是怎么工作的、参数在哪、时序如何、扩展点在哪"。
> 规划过程与踩坑记录见 `docs/传输层规划.md`；架构主线见 `docs/混合路由规划.md`。

## 一、先说清楚现状：局域网通了，公网还没接

| 场景 | 状态 | 说明 |
|---|---|---|
| **同一局域网**（手机连家里 WiFi） | ✅ **已实测可用** | `python run.py --serve-remote`，手机开 `https://192.168.0.8:8801/` 即可按住说话 |
| **外网**（4G/5G、公司网） | 🟡 **设计已完成，入口未接通** | 代码侧已就绪（协议、TLS、鉴权全部实现）；缺的是"公网流量怎么进到这台机器"这一步 |

**为什么公网只差"入口"这一步**：整套实现是 **客户端主动外连** 的结构 ——
手机作为 WebSocket 客户端连出来，服务端不需要被公网主动访问。
所以只要有一条"手机能到达服务端"的通道即可，服务端代码不用改。

已实测的网络条件（`tools/probe_ingress.py`）：

| 观测 | 值 | 含义 |
|---|---|---|
| DNS | `yyssccy.fnos.net` → `113.200.130.211`，无 AAAA | 纯 IPv4 |
| PTR 反查 | 该 IP 反查回 `yyssccy.fnos.net` | **是自家公网 IP，不是厂商中转池** |
| 证书 | Let's Encrypt，CN=`yyssccy.fnos.net` | NAS 侧已有受信证书，自动续期 |
| NAS | nginx 监听 80/443/5666/5667 | 已有统一入口 |

**待确认的一件事**：NAS 的「统一网关 / 反向代理」能否添加一条指向**内网任意 `IP:端口`** 的规则。
能加 → 三节里的"方案 A"成立；不能 → 用"方案 B/C"。

## 二、端到端链路

```
┌─────────────── 手机浏览器（web/）────────────────┐
│ 麦克风 → AudioWorklet 采集                        │
│        48k/立体声 → 降混 → 线性重采样 → 16k/单声道 │
│        → 攒成 512 帧(32ms) → Int16 → 二进制帧      │
│                                    ↓ 上行          │
│ 扬声器 ← WebAudio 排程播放（currentTime 时间轴）   │
│                                    ↑ 下行          │
└───────────────────────┬──────────────────────────┘
                        │  一条 WSS 长连（双向复用）
                        │  上行音频 / 下行 TTS / 控制与事件
┌───────────────────────┴──────────────────────────┐
│ 服务端 transport/websocket.py                     │
│  握手鉴权 → 会话绑定 phone:xxxx → 上行入队          │
│  上行泵（队列+丢最老）→ pipeline.feed_audio()      │
│  pipeline 产出 → 下行队列 → 发送协程 → 二进制帧     │
│  主动播报（委托进度/结果）→ 独立队列                │
└───────────────────────┬──────────────────────────┘
                        │ 与语音链路**完全相同**的一段
                        ▼
   VAD 判句 → STT → LLM(工具轮次) → TTS（见 backend/）
```

一句话：**手机对 `pipeline` 而言就是一块"网线接过来的声卡"**。
编排、VAD、唤醒、工具轮次、委托播报、落历史全部复用，一行未改。

## 三、公网入口怎么接（三选一）

服务端本身不需要改动，只是"让流量能到达 `192.168.0.8:8801`"。

### 方案 A：服务部署到 NAS + 网关注册（推荐）

```
手机 → https://yyssccy.fnos.net/voice (WSS)
         └─ NAS nginx / 统一网关 → 服务进程（NAS 本机）
```

* **优点**：同机一跳，无额外转发；复用现成的 Let's Encrypt 证书（手机**无需信任自签**）；
  路由器**一条映射都不用开**；NAS 7×24 开机，PC 可以关。
* **前提**：网关支持添加自定义目标（待确认）。
* **注意**：手机作为音频端时，**NAS 不需要声卡** —— VAD 是纯计算，STT/TTS 都在云端，
  唤醒词在手机本地（规划中）。所以服务层可以完全无音频设备运行。

### 方案 B：服务留在 PC，NAS 反代进来

```
手机 → NAS:443 → nginx → http://192.168.0.8:8801
```

* 适合"想先在 PC 上验证、暂不迁移"。
* 需要 NAS 能访问 PC 的内网地址（当前同网段，满足）。
* 注意：反代要**透传 WebSocket**（`Upgrade`/`Connection` 头 + 长连接超时调大）。

### 方案 C：路由器端口映射 + 服务自己出证书

* 需要公网 IP + 路由器管理权限；新开一个端口映射到本机 `8801`。
* 若复用 `yyssccy.fnos.net`，证书 CN 不匹配 → 手机仍会警告；建议直接用 IP + 自签。

> ⚠️ **安全红线**：无论哪种方案，都**不要**把 `127.0.0.1:3080`（DSH Web GUI，
> 内含全权限 agent）暴露到公网。挂公网入口**必须打开口令**（`--no-auth` 只用于内网调试）。

## 四、协议

协议是**客户端与服务端的唯一契约**，纯编解码实现放在 `protocol/__init__.py`
（不 import 任何网络库，因此可离线单测：`tests/offline/f2_remote_server.py`）。

* 协议版本：`PROTOCOL_VERSION = 1`
* 握手期校验版本；不一致 → **`bye("version mismatch")` 并断开**
  （注意：当前实现只发 `bye`，不发 `error`；`E_BAD_VERSION` 常量已定义但未使用 ——
  客户端若要与版本做交互式协商，这里需要补一条 `error`）

**实际会用到的错误码**（其余常量已定义但暂未使用）：
`bad_message`（坏帧/首帧不是 hello/未知控制帧）、`unauthorized`（口令不符）。
`E_BAD_VERSION` / `E_DUPLICATE` / `E_INTERNAL` 为预留：目前版本不符走 `bye`，
重复连接与内部错误还没有独立处理分支（内部错误目前只在服务端日志里可见）。

### 4.1 音频格式（全链路统一）

| 参数 | 值 | 为什么 |
|---|---|---|
| 采样率 | 16000 Hz | 与本机 `adapter` 采集格式一致 → **零重采样、零解码** |
| 位深 | 16 bit | 同上 |
| 声道 | 1（单声道） | 同上 |
| 分块 | 512 帧 = **32 ms** | 与本机 `input_chunk_size=512` 一致 → VAD 判句粒度与既有基线可直接沿用 |
| 压缩 | **不压缩**（原始 PCM） | 省 CPU、不引入压缩缓冲延迟；约 256 kbps 可接受。base64 会白增 33% 体积 |

采样率差异在**手机侧**处理：AudioWorklet 把浏览器原生（通常 48k、可能立体声）降混+重采样成 16k。

### 4.2 二进制帧（4 字节头）

```
byte 0     类型：0x01 = 上行音频（手机→服务端）  0x02 = 下行音频（服务端→手机）
byte 1     保留（0）
bytes 2-3  小端 uint16 序号（回绕）—— 用于丢帧检测与时延排查
──────────────────────────────────────────────
其后为 PCM 数据
```

### 4.3 控制帧（JSON 文本）

**手机 → 服务端**

| 类型 | 字段 | 说明 |
|---|---|---|
| `hello` | `version, token, sampleRate, frameSamples` | **必须首帧**。服务端 `wait_for(recv, timeout=10)`，10 s 内没收到就回 `error[bad_message]` 并断开 |
| `start` | — | 用户按下按钮（开始一轮说话） |
| `end` | — | 用户松开 |
| `cancel` | — | 打断当前轮 |
| `ping` | `t` | 延迟探测（客户端时间戳） |

**服务端 → 手机**

| 类型 | 字段 | 说明 |
|---|---|---|
| `ready` | `protocol, sessionId, sampleRate, frameSamples, speaking` | 握手成功 |
| `state` | `idle, speaking, recording` | **状态机权威**，客户端据此决定能否推流 |
| `stt` | `text` | 识别结果（让用户看到"我听成了什么"） |
| `text` | `text` | 助手这一轮说的话（**只在 `final` 给一次**，音频块不夹带文本） |
| `announce` | `text` | 主动播报（委托进度/结果） |
| `turn` | `phase: start\|end`, `outcome` | 轮次边界（客户端做进度反馈） |
| `notice` | `code, message` | 非错误的提示（"没听清"这类） |
| `pong` | `t` | 回显客户端时间戳 |
| `error` | `code, message` | 错误，**按 code 分支**，不要匹配 message |
| `bye` | `reason` | 服务端主动断开（鉴权失败等） |

**错误码**：`bad_version` / `unauthorized` / `bad_message` / `duplicate_session` / `internal`
**提示码（notice.code）**：`no_speech`（没听清）/ `no_answer`（没能回答）/ `delegated`（已转后台）/ `turn_error`

### 4.4 一轮完整时序

```
手机                                     服务端
 │ ── hello(token) ─────────────────────→ │  校验版本+口令
 │ ←──────────────── ready(sessionId) ─── │  建会话、绑定注册表、按需唤醒
 │ ── start ────────────────────────────→ │  标记"用户在说话"
 │ ←──────────────── state(idle=true) ─── │  ★ 按下不该被拦（见第六节）
 │ ── 音频块 × N（32ms/块，实时速率）────→ │  入队 → 上行泵 → VAD 攒句
 │                                         │  静音 ≥0.5s → 判句 → STT → LLM → TTS
 │ ←──────────────── stt(识别文本) ────── │  立刻回显，用户知道听成了什么
 │ ←──────────────── state(idle=false) ── │  正在处理
 │ ←──────────────── 音频块 × M ───────── │  TTS 首个音频包**一到就发**
 │ ←──────────────── text(完整回复) ────── │  音频块不夹带文本（否则刷屏）
 │ ←──────────────── turn(end, ok) ────── │  轮次收尾
 │ ←──────────────── state(idle=true) ─── │  ★ 恢复可发言（否则按钮卡死）
 │ ── end ──────────────────────────────→ │
```

## 五、服务端实现（`transport/websocket.py`）

### 5.1 一个端口同时做三件事

用 `websockets` 的 `process_request` 钩子，在**同一端口**上同时提供：

| 请求 | 处理 |
|---|---|
| WebSocket 升级（`Upgrade: websocket`） | 放行给握手处理 → 音频链路 |
| `GET /health` | 返回 JSON 状态（协议版本、连接数、会话、是否需鉴权、证书指纹） |
| 其他 GET | 从 `web/` 提供静态文件（只读；路径规范化后必须在 `web/` 内，拒绝 `../` 穿越） |

> ⚠️ **必须按 `Upgrade` 头放行**：`process_request` 在握手**之前**被调用，
> 若无脑当静态请求处理，`/ws` 会因"找不到文件"返回 404，客户端直接连不上。

### 5.2 三条队列（这是低时延与不卡死的关键）

| 队列 | 容量 | 满时策略 | 为什么 |
|---|---|---|---|
| 上行 `uplink` | 128 块（≈4 s） | 丢**最老** | 网络读协程只做"入队"，绝不在读循环里 `await feed_audio`，否则下游一慢就把网络读也拖住 |
| 下行 `downlink` | 40 块（≈1.3 s） | 丢**最老** | 宁可让用户听到"跳过一小段"，也不让整条链路积压到秒级延迟 |
| 播报 `announce` | 12 块 | 丢最老 | 委托结果单独一条队列，不被长回复挤掉 |

**优先级**：本轮 TTS 音频 > 主动播报。播报是异步结果（等多久都还能再说），
而用户正等着听回复 —— 让播报插到前面会明显打断对话。

### 5.3 上行泵

音频到达 → 入队 → 由独立协程 `_uplink_loop` 取出并 `await pipeline.feed_audio()`。
单块处理耗时若接近 32ms（分块时长），说明服务端跟不上实时 —— `debug` 模式会告警。

**懒启动**：上行泵在**收到第一个音频块**时就启动，而不是只在收到 `start` 控制帧时。
（客户端可能先推流后补 `start`；只在 `start` 时启动会让音频永远堆在队列里。）

### 5.4 发送协程

按优先级取队列（都空则 `asyncio.wait(FIRST_COMPLETED)` 等待，不忙等），
给音频加 4 字节头后 `ws.send()`。**队列里所有元素统一是 `(kind, payload)` 元组** ——
混用裸字节和元组会让 unpack 崩掉，表现为"客户端一直收不到音频"。

### 5.5 静态页与证书

| 设置 | 值 | 原因 |
|---|---|---|
| `Cache-Control` | `no-store` | 开发期改完刷新即生效，免得用户清缓存 |
| MIME | 按扩展名映射，`.js` 用 `application/javascript` | **AudioWorklet 要求正确 MIME**，否则 `addModule` 失败 |

## 六、状态机：客户端"能不能按"由服务端回答

### 6.1 `state` 的语义

服务端推的 `state` 是**唯一权威**：

| 字段 | 含义 |
|---|---|
| `idle` | 服务端现在能接新的一轮吗（见下） |
| `speaking` | 正在往你这边送音频（在放音） |
| `recording` | 服务端认为你正在说话 |

客户端规则：**只在 `idle && !speaking` 时允许按下**。

### 6.2 `idle` 对远端与本机的判据不同（关键设计）

```
本机会话：有进行中轮次 / 扬声器在放音 / VAD 在录音 / 任意远端在说话 → 忙
远端会话：有进行中轮次 / **它自己是否正在放音** → 忙
```

**为什么远端不看 `recording`**：客户端的 `start` 会先到服务端，如果"用户在说话"被算作忙，
服务端立刻回 `idle=false`，客户端据此拒绝下一次输入 —— **它用"自己在说话"这个事实把自己锁死了**。
远端的忙只该看两件事：有没有进行中的轮次、它自己是否在放音。

**为什么本机侧不看远端录音**：本机回声抑制会吃话，必须在录音时闭嘴；
远端由手机自己静音麦克风（`echoCancellation` + 播放时暂停采集）。

### 6.3 状态推送的时机（漏一个就会卡界面）

| 时机 | 目的 |
|---|---|
| `start` / `end` / `cancel` | 即时反映用户操作 |
| 每轮 `final`（**延迟 0.15s**） | 轮次结束后恢复可发言 |
| 轮次结果通知（`turn` end） | 同上，双保险 |

> **0.15s 延迟的原因**：`invoke` 是在 `yield final` **之后**才清 txn 的，
> 立刻读会读到"仍然忙"，等于没修。
>
> 实测踩过的坑：用户"松开"那一刻正好是 txn 非空的瞬间，服务端回 `idle=false`（正确），
> 但**之后再没有任何 state 推送** → 按钮永久停在"稍等…"。

### 6.4 客户端看门狗

客户端**不完全信任**服务端状态：忙超过 `MAX_BUSY_MS = 20s` 就本地解锁并提示。
宁可让用户重试，也不要让他对着一个死界面。

### 6.5 三轮收尾必须都有交代（"永不静默"）

任何一轮结束都通过 `pipeline.on_turn_outcome` 上报结果，服务端推 `notice` + `turn`：

| outcome | 客户端文案 |
|---|---|
| `ok` | 已回复 |
| `delegated` | 已转后台处理 |
| `no_speech` | 没听清，请再说一次 |
| `no_answer` | 这轮没能回答上来 |
| `turn_error` | 这轮出错了 |

**为什么必须有**：STT 返回空时 pipeline 原本直接 `return`，客户端什么都收不到，
用户看到界面永远停在"稍等…"，以为助手死了。

## 七、TLS：不是"更安全"，而是**可用性前提**

浏览器**只在安全上下文**里把麦克风给页面。`http://192.168.0.8:8801` 属于不安全来源
（`http://localhost` 是例外）→ Chrome **直接拒绝** `getUserMedia`，现象是"按住没反应"。

所以 `--serve-remote` **默认开启 TLS**（`--no-tls` 仅调试用）。

### 7.1 自签证书（`transport/tls.py`）

| 项 | 值 |
|---|---|
| 生成 | 首次运行自动生成到 `data/certs/`，之后**复用**（否则手机每次都要重新信任） |
| 算法 | RSA 2048 / SHA256 / 825 天 |
| SAN | **必须带 IP SAN**（主机名进 DNS SAN，IP 进 IP SAN） |
| 参数 | `--tls-dir` 自定义目录；启动时打印**证书指纹**供核对 |

> ⚠️ **只写 CN 不带 IP SAN 的话，现代浏览器会"直接拒绝连接"**（不是只警告）——这是必错点。
>
> ⚠️ 私钥权限只在 **POSIX** 上收敛为 `0600`。Windows 的 `chmod` 只映射只读位，
> 对目录设 `0o600` 会把它变成**拒绝访问**（实测把临时目录都弄坏了）。

### 7.2 手机端首次访问

会提示"不安全" → 选「高级 → 继续访问」。要核对身份就看启动时打印的证书指纹。

自签是**局域网方案的固有代价**（IP 签不出公信证书）。走公网入口（方案 A）时可用现成的
Let's Encrypt 证书，手机不再需要这一步。

## 八、鉴权

| 模式 | 启动参数 | 行为 |
|---|---|---|
| 随机口令（默认） | `--serve-remote` | 启动时生成并打印；手机端输入一次后会记住（localStorage） |
| 指定口令 | `--token mypass` | 固定口令 |
| 不鉴权 | `--no-auth` | 手机端口令留空直接连。**仅内网调试**；挂公网前务必恢复 |

流程：客户端在 `hello` 里带 `token` → 服务端比对 → 不符则回
`error[unauthorized]` + `bye` 并断开（同时日志记录来源 peer）。

**状态可见**：`/health` 返回 `authRequired`，便于确认当前是否裸奔。

> 长期方案（阶段 5）建议改成**一次性配对换取长期凭据**，而不是每次手输口令。

## 九、网页端实现（`web/`）

| 文件 | 职责 |
|---|---|
| `index.html` | 界面：口令输入、按住说话按钮、状态/延迟/丢帧、日志区 |
| `app.js` | WS 客户端、播放排程、状态机、看门狗、回声防护 |
| `capture-worklet.js` | 采集：降混 + 线性重采样 + 32ms 分块 |

### 9.1 采集为什么用 AudioWorklet

`ScriptProcessorNode` 跑在**主线程**且已废弃 —— 主线程一卡（渲染、GC）就丢音频，
而丢音频等于"用户说的话缺一块"，直接损坏 STT 与 VAD 判句。
AudioWorklet 跑在专用音频线程，不受主线程影响。

重采样放在 worklet 里做等于**零延迟成本**：数据还没过网络就已经是目标格式。
线性插值保留跨块的相位小数部分，避免每块重新对齐造成的抖动。

### 9.2 播放为什么排程到 AudioContext 时间轴

```js
const when = Math.max(ctx.currentTime + PLAY_LEAD, state.nextPlayTime);
src.start(when);
```

用 `setTimeout` 逐块拼接，每块都有抖动，几十块累积起来就是明显的断续/爆音。
排程到 `currentTime + 缓冲余量`（`PLAY_LEAD = 0.12s`）可让 WebAudio 在采样级无缝衔接。

### 9.3 三处防御（都对应实测踩过的坑）

| 防御 | 原因 |
|---|---|
| **`onopen` 里立刻发 `hello`，不做任何 `await`** | 曾经先 `await ensureAudio()`（载入 worklet + 弹麦克风权限）才发 hello，手机上权限弹窗一停几秒 → 服务端 10s 握手超时 → 用户看到"连不上"。**握手不能被 await 拖死** |
| **麦克风改到按下按钮时申请** | 在用户手势里弹权限是浏览器推荐做法；弹窗也只出现一次 |
| **安全上下文预检** | 若页面不是安全上下文，直接给出可执行的提示（用 http 打开时必然遇到） |

### 9.4 回声处理

* `getUserMedia({echoCancellation: true, noiseSuppression: true, autoGainControl: true})`
* 播放期间客户端**暂停采集**（相当于本机 `cancel_echo` 的对等物）

**戴耳机可完全规避**；免提时若仍有回声，下一步应做服务端 AEC 或缩短播放窗口。

## 十三、对外接口（扩展用）

### 13.1 新增一个音频端（例如原生 App / 桌面客户端）

实现 `transport.AudioTransport` 的五个方法，注册进 `TransportRegistry` 即可，
`pipeline` 无需改动：

```python
class MyTransport(AudioTransport):
    session_prefix = "app:"          # 会话前缀（用于路由）
    is_local = False

    async def start(...): ...        # 建立连接、开始收音频
    async def feed_audio(chunk, session_id): ...      # 上行交给 pipeline
    async def handle_response(response): ...          # 下行（音频/文本）
    async def stop_response(session_id, context_id) -> bool:
        ...                          # 返回"是否真的中断了播放"（决定落历史）
    def is_recording(session_id=None) -> bool: ...    # 仲裁用
    def is_active(session_id=None) -> bool: ...       # 仲裁用（断开后必须 False）
    def is_playing(session_id=None) -> bool: ...      # 仲裁用：远端"忙不忙"
    async def emit(text, session_id=None): ...        # 主动播报怎么"说"
```

### 13.2 服务端用到的 pipeline 钩子

| 钩子 | 用途 |
|---|---|
| `pipeline.attach_transport(registry)` | 接管下行路由与仲裁 |
| `pipeline.on_turn_outcome(cb)` | 每轮结果（ok / no_speech / delegated / turn_error） |
| `pipeline.on_transcript(cb)` | 识别结果，用于回显 |
| `pipeline.request_wake(sid, reason)` | 远端按需唤醒（不喊唤醒词） |
| `pipeline.MIN_STT_DURATION` / `TXN_STALE_AFTER` | 过短片段阈值 / 卡死轮次自愈 |

### 13.3 HTTP 控制面

| 方法 | 路径 | 返回 |

| GET | `/health` | `{ok, protocol, sampleRate, frameBytes, tls, tlsFingerprint, connections, sessions, authRequired, speaking[]}` |
| GET | `/` 及 `/xxx.js` | `web/` 下的静态文件（只读） |
